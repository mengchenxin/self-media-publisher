# 自媒体多平台发布

把「一个选题」变成「五个平台上的五篇不同文章，并且真正发出去」。

本 skill 的价值不在于写文章（模型本来就会写），而在于三件模型默认做不好的事：

1. **平台差异的硬规格** —— 各平台字数、比例、话题上限、发布入口都不同，凭印象写必错。
2. **发布的真实操作序列** —— 浏览器自动化发布有一堆坑（富文本不认 Markdown、话题必须点联想、SPA 输入不生效）。
3. **发布前的合规门禁** —— 广告法绝对化用语和导流词是中国平台限流的头号原因。

---

## 何时使用 / 不使用

**使用**：用户要从选题一路做到发布，或要把已有文章铺到多个自媒体平台。

**不使用**：
- 用户只是要写一篇文章、不需要分发 → 直接写，不必走全流程。
- 用户只要发到单个平台且已写好稿 → 直接跳「阶段 7 发布」。
- 平台账号需要企业资质认证而用户没有 → 明确告知，不要硬试。

---

## 阶段 0：前置确认（不可跳过）

开工前先确认五件事，缺任一项都要问用户，**不要猜**：

1. **目标平台清单** —— 本次要发哪几个。
2. **账号状态** —— 每个平台是否已有账号、是否有发布权限。
   - 头条未实名 → 只能存草稿；小红书新号 → 风控期；公众号 → 是否有群发权限。
3. **输入来源** —— 用户给选题，还是给素材/大纲，还是要先做选题调研。
4. **输出目录** —— 默认 `./<文章slug>/`，含 `master.md` 及各平台版本。
5. **浏览器 profile** —— 首次跑必须确认用哪个登录态载体（见下）。

把「平台清单 + 账号 + 默认受众 + 语气偏好」记入工作区长期记忆，下次不必重复问。

### 浏览器 profile（决定能不能自动发布，必须显式设置）

**`agent-browser` 默认用临时 profile，登录态不跨轮保留。** 因此发布前必须选定一种登录态载体：

| 方案 | 何时用 |
| --- | --- |
| `--profile <固定目录>`（推荐） | 长期使用。首次人工登录各平台一次，之后复用 |
| `--profile Default` | 平台已在你日常 Chrome 登录过，想直接继承。**需先完全退出 Chrome** |
| `--session-name <名字>` | 轻量方案，只存取 cookies + localStorage |

首次使用「固定目录」方案时，需要**引导用户手动登录 5 个平台一次**，并逐平台 `state save` 备份登录态。这一步没法自动化，要如实告诉用户。

命令行细节、代理问题、参数生效时机见 `references/publish-runbook.md` 第一节。**发布前必读。**

> 若用户表达「发到所有平台」，先用 `references/platform-specs.md` 第四节核对账号前提，把**做得到的平台**列出来让用户确认，而不是假装全都能发。

## 阶段 1：选题与调研

按输入来源二选一：

- **用户给了选题** → 做一轮事实核查：找 2–3 个可引用的数据或案例，记录来源与年份。
- **用户没给选题** → 产出 5 个候选选题，每个含「受众 + 钩子 + 差异化角度」，让用户挑。

检索工具优先级：`WebSearch`（事实、热点、数字）→ `WebFetch`（读具体页面）。金融/投资类选题才用 `agentic_search`，普通选题不要用。

**调研产出**：一份带来源的事实清单。没有来源的数字一律标 `未核实`，后续不允许进入任何平台版本。

---

## 阶段 2：写作母稿

依据 `assets/article-template.md` 的结构写出母稿，落到 `<输出目录>/master.md`。

母稿是**唯一事实容器**，长度按最长平台写（3000–4000 字），按信息块组织（`[HOOK]` `[THESIS]` `[ARG-n]` `[CASE]` `[GOLD]` `[ACTION]` `[LIMIT]`），因为改写阶段要按块拆装。

写作要求见 `references/rewrite-playbook.md` 第二节。

---

## 阶段 3：一稿多改

读 `references/platform-specs.md` 拿规格、`references/rewrite-playbook.md` 拿方法，为每个目标平台产出 `<平台>.md`。

**核心约束：不是删减，是重写。** 至少三处实质差异（标题、开头、段落顺序或案例），否则平台间重复度检测会互相压流量。

每个平台产出后逐条过 `references/rewrite-playbook.md` 第六节的检查清单。

标题每个平台出 3 个候选，让用户挑，把选中的记进台账备注。

---

## 阶段 4：配图

**文字类卡片一律用 HTML 渲染 + 浏览器截图，不要用 ImageGen。** ImageGen 渲染中文长文本会糊字、缺笔画，而小红书首图恰恰需要精确大字排版。

```
python scripts/render_card.py --title "居家办公3年|我以为很爽|结果效率崩了" \
                              --kicker "远程办公 / 效率" --footer "@用户账号" \
                              --theme ink --out <输出目录>/images/xhs-1.html
```

标题里的 `|` 是强制换行 —— 首图断行位置对可读性影响极大，要手工控制。

截图顺序**不能乱**（`set viewport` 会重置页面，必须设完再打开一次），完整命令和踩坑记录见 `references/publish-runbook.md` 第七节。截完用 Read 工具看图，确认页脚没被挤出、标题没溢出。

- 比例：公众号封面 2.35:1、小红书首图及正文图 3:4 竖版。比例错了发布页会裁切，是最常见的返工点。
- 图片总量：小红书 3–9 张，微博 ≤9 张，其余平台 2–4 张。
- 非文字类配图（场景图、示意图）才用 `ImageGen`。
- 所有图放 `<输出目录>/images/`。

若用户不需要配图，跳过本阶段并在台账备注中注明。

## 阶段 5：预检（发布前的硬门禁）

一条命令查三类问题：**平台规格 + 合规 + 版本间重复度**。

```
python scripts/preflight_check.py <输出目录>
```

| 检查项 | 不通过会怎样 |
| --- | --- |
| 标题/正文字数 | 超硬上限会被平台截断（头条标题 >30 字、小红书标题 >20 字） |
| 话题数量 | 没填够拿不到冷启动流量 |
| 图片张数与像素比例 | 比例不对发布页直接裁切 |
| 广告法绝对化用语、导流词、手机号 | 限流甚至违规 |
| 版本间重复度 | 平台互相压流量（标题相同或正文 3-gram 相似度 ≥60% 直接判不合格） |

其余规则：

- **`verdict = BLOCK` → 必须回改，不许发布**（含 FAIL 项和合规 BLOCK 命中）。回改后重跑直到通过。
- WARN 项逐条判断，可保留但要在给用户的汇报里说明理由。
- 退出码非 0 即代表 BLOCK，可作为流程门禁。
- `--show-specs` 查看平台规格表；`--json` 便于程序化处理。
- 只需查违禁词时，可单跑较轻的 `scripts/compliance_check.py`。
- 规格表在 `scripts/preflight_check.py` 的 `SPECS` 里，与 `references/platform-specs.md` 同步维护 —— 平台改版时两边都要改。

## 阶段 6：发布（浏览器自动化）

**完整操作手册：`references/publish-runbook.md`。发布前必读该文件。** 这里只列不可违反的规则：

**先做幂等检查 —— 这是发布前的第一件事：**

```
python scripts/publish_log.py check --log <输出目录>/publish-log.csv --article "<标题>"
```

退出码 1 表示该文章已有平台发过，**默认跳过这些平台**。重复发布的代价很高（公众号群发一天只有一次机会），只有内容已改动或上次被限流才重发 —— 那属于明确决定，不是默认行为。

0. **必须带 profile 启动。** 第一条命令固定写成：

   ```
   agent-browser close --all        # 换参数前必须先关，否则参数被静默忽略
   agent-browser --args "--no-proxy-server" \
                 --profile "<阶段 0 选定的 profile 路径>" \
                 open <第一个平台发布页>
   ```

   不带 `--profile` 就是临时 profile，登录态不跨轮保留。`--profile` / `--args` **只在启动守护进程那次生效**。

1. **先草稿，后发布。** 填完表单 → `screenshot` → **把截图给用户** → 得到明确确认后才点最终发布按钮。
2. **不替用户登录。** 遇到登录页/验证码/扫码，暂停并请用户手动完成。
3. **不伪造结果。** 没真发出去就不能写 `published`。
4. **整轮只 `close` 一次**，放在最后（含失败路径），中途 `close` 会让下一个平台丢失会话。
5. **每个平台发布前都重新探测登录态** —— 同一个会话里换个平台也可能已掉线。用 `snapshot` 判断，**不要用 `eval "document.cookie"`**（实测读不到）。
6. **先验证连通性再动手。** `open` 后 `get url`，若是 `chrome-error://chromewebdata/` 说明代理/网络不通，先解决，别往发布页填表。
7. 选择器失效时用 `snapshot -i` 重新取元素，**以页面为准**，不要反复重试同一命令。
8. **新平台第一次发布先 dry-run。** 只填表不点发布 —— 停在草稿 + 截图确认字段和选择器都对，再正式发。第一次就真发，出问题时已经发出去了。

单平台失败不阻断其他平台：记录状态后继续下一个。

## 阶段 7：台账与汇报

```
python scripts/publish_log.py init    --log <输出目录>/publish-log.csv
python scripts/publish_log.py add     --log ... --article "<标题>" --platform 公众号 \
        --status published --url "<链接>" --file wechat.md
python scripts/publish_log.py summary --log ... --article "<标题>"
```

状态取值：`draft` / `pending_review` / `published` / `published_no_image` / `failed:<原因>` / `blocked:<原因>` / `skipped:<原因>`。

小红书统一记 `pending_review`，提醒用户 48 小时后回查是否限流。

最后向用户汇报一张表：平台 / 状态 / 链接 / 备注。**未成功的平台必须说明卡在哪一步、需要用户做什么。**

**汇报时必须一并约定数据回收时点**（不约定的话这一步永远不会发生）：

> 「建议发布后 24 小时和 72 小时各回抓一次数据，你希望到时候提醒你，还是你自己来叫我？」

## 阶段 8：数据回收

发布不是终点。**在 24h 和 72h 各回抓一次**各平台的数据，写入独立的数据台账：

```
python scripts/stats_log.py init   --log <输出目录>/stats-log.csv
python scripts/stats_log.py add    --log ... --article "<标题>" --platform 公众号 \
        --age 24h --reads 860 --likes 34 --comments 12 --shares 8
python scripts/stats_log.py report --log ... --article "<标题>"
```

完整操作步骤见 `references/publish-runbook.md` 第六节，各平台数据后台地址与指标口径见 `references/platform-specs.md` 第五节。

三条硬规矩：

1. **抓不到就留空，不要填 0。** 「0」和「未知」在复盘时是完全不同的信息。
2. **canvas 图表抓不到数值时，截图交给用户读**，不要编造数字。
3. **不要发布后立刻抓** —— 数据还在跳，此时数字没有复盘价值。

`report` 会算出 24h → 72h 的阅读增幅，据此判断：持续增长→同题材再做；几乎不涨→换标题重发；某平台显著偏低→回看该平台的改写。

> 本阶段天然是延迟的（要等 24h）。如果用户需要自动提醒，用 `automation_update` 建一个一次性任务在 24h 后触发；**不要为了「完成全流程」而跳过或伪造这一阶段**。

## 红线汇总

| # | 红线 |
| --- | --- |
| 1 | 未获用户明确确认，不点最终发布按钮 |
| 2 | 有 BLOCK 级合规命中，不发布 |
| 3 | 不代用户登录、不绕过验证码 |
| 4 | 不伪造发布结果，失败就写失败 |
| 5 | 母稿中 `未核实` 的事实，不出现在任何平台版本 |
| 6 | 缺少账号或权限的平台，如实标记跳过，不硬试 |
| 7 | 数据回收抓不到的指标留空，不填 0、不编数字 |
| 8 | 启动 agent-browser 必须带 `--profile`（否则登录态不保留）且先确认网络连通（代理会导致静默失败） |

## 首次使用建议

首次上手按这个顺序，不要跳步：

1. **安装浏览器**：`npm install -g agent-browser && agent-browser install`（约 200MB，装到 `~/.agent-browser/`）。若已装过则跳过。
2. **验证连通性**：带上 `--profile` 启动并 `agent-browser get url`，确认不是 `chrome-error://`。若环境有 `HTTP_PROXY` / `HTTPS_PROXY`，需加 `--args "--no-proxy-server"` 或换成可用代理。
3. **只挑 1 个平台登录并跑通全流程**（推荐微博：门槛最低、字数最少）。这一轮的目的是验证登录态能跨 `close` 保留 —— 登录 → `close` → 重开 → `snapshot` 看是否还在登录状态。**这一步不通过，后面的多平台铺开都是空谈。**
4. **通过后再登录其余平台**，每个平台登录成功后 `agent-browser state save <输出目录>/auth-<平台>.json` 备份。
5. **最后才铺多平台**。一上来就发五个平台，出问题时定位成本极高。
